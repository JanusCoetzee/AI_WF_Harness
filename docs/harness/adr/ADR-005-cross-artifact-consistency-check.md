# ADR-005 — G5 traceability check becomes a scripted full REQ trace, not a new skill

| Field | Value |

| Status | Accepted |

## Context

A comparison against `github/spec-kit` surfaced its `/speckit.analyze` step: a
cross-artifact consistency check that diffs spec, plan, and tasks for drift
against each other before implementation proceeds.

This harness already requires a traceability spot-check at G5 ("pick 3 REQs,
walk them to code+tests" — `gates/GATES.md`), but it's a manual sample, not a
systematic check. `REQ-###`/`CHG-###` tags are already mandatory in commits,
tests, ADRs, and PRs (`CLAUDE.md` §5), which means the data needed for a full
trace already exists in the repo — it's just never assembled into one view.
If we don't decide anything here, drift between what the PRD promised and what
the PLAN/code actually built can pass a 3-sample spot-check by chance.

## Options considered

### Option A — New `/harness-analyze` skill, standalone gate evidence

- Sketch: a skill that diffs REQ-### coverage across `PRD.md` ↔ ADRs ↔
  `PLAN.md` ↔ code, producing a drift report required as G3 (or G5) evidence.
- Pros: explicit, repeatable, produces an artifact reviewers can read directly
  instead of re-deriving consistency by eye.
- Cons: another new skill to maintain; overlaps with the traceability
  spot-check already required at G5.
- Risks: redundant ceremony if it duplicates the G5 spot-check rather than
  strengthening it.

### Option B — Extend the existing G5 traceability spot-check from 3 REQs to all REQs, automated

- Sketch: keep the check inside `harness-review` (no new skill), but change
  the gate evidence from "spot-check 3 REQs" to "full REQ ↔ ADR ↔ PLAN ↔ code
  mapping table, generated by grepping REQ-### references across the repo."
  Cheap to script since REQ-### is already a required tag in
  commits/tests/ADRs.
- Pros: strictly stronger than today's 3-REQ spot-check for near-zero added
  process; no new stage or skill; scriptable (`grep -rn 'REQ-[0-9]\+'`).
- Cons: full coverage is a heavier read for the reviewer than 3 spot-checked
  REQs; needs a script to be worth doing (manual full-trace is tedious enough
  that it will erode back to spot-checking).
- Risks: if the script isn't written, this option degrades to Option A's
  "reviewer eyeballs everything," which doesn't scale past a handful of REQs.

## Decision

**Option B.** Strengthen the existing G5 spot-check into a scripted full
REQ-### trace rather than adding a parallel skill. Requires a small script
(`scripts/`) to grep REQ-###/CHG-### references across PRD, ADRs, PLAN, tests,
and commits, and render a mapping table — not a new stage.

AI recommendation: Option B — a new skill (Option A) would duplicate G5's
existing mandate rather than close its actual gap, which is sample size, not
missing tooling.

## Consequences

**Easier:** reviewers get a full traceability table instead of a 3-sample
spot-check, for near-zero added process once the script exists.

**Harder / new commitments:** the REQ-trace script is new tooling that must be
kept working as the repo's commit/test conventions evolve; if it silently
breaks (e.g. a tagging convention drifts), G5 quietly reverts to manual
spot-checking without anyone deciding that.

**Tripwire to revisit this ADR:** if the script proves too brittle to
maintain (frequent false negatives/positives from tagging drift), reconsider
Option A — a dedicated skill with its own judgment calls may handle edge
cases a grep-based script can't.
